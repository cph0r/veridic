# Simplify Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** People see three words (part, spec, rule), each part has one spec, and the dashboard lists parts — with nothing that worked before broken and no metric dropped.

**Architecture:** A metrics baseline is captured first and compared at the end. The report model groups spec files into parts (by the code their rules cite, then folder name, then "Other specs") and the dashboard table becomes a table of parts. `moduleList` gives each part one main `spec_path`; `veridic parts` aliases `veridic modules`. User-facing prose changes wording; JSON keys and flags do not.

**Tech Stack:** Node ESM, node:test. No new dependencies.

**Spec:** docs/specs/2026-10-23-simplify-design.md

## Global Constraints

- JSON keys, flags and command names stay as they are (`modules`, `--module`, `requirements`, `specs`); only human-readable text changes. `veridic parts` is added, `veridic modules` stays.
- No metric is dropped: every number the report JSON, `veridic coverage` and the dashboard showed before is still computed with the same value (headline totals equal the sum over spec files).
- Rule ids (FR-002, INV-1) stay visible, shown small.
- Private client apps are never named in this repo ("App A"); commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- `npm test` stays green after every task.

## Review Focus

1. A spec file whose rules cite code in two parts equally: it goes to one part, deterministically (the first by part order), never both (Task 2 test `a spec citing two parts equally goes to the first`).
2. A spec with no citations and no matching folder: shown under "Other specs", never lost from totals (Task 2 test `a spec with no part is in Other specs and in the totals`).
3. A repo with specs but no modules or screens (a library): each spec is its own part row, as the table shows today (Task 2 test `without parts, each spec is its own row`).
4. A part with no spec: a row with health "No spec", 0 rules, its Covered count, and it doesn't change headline rule totals (Task 2 test `a part with no spec is a row and adds no rules`).
5. The opened part shows every rule of every file, grouped by file, and opening by rule id (cards' "data-rule") still finds a rule in any of the part's files (Task 3 test `opening a rule finds it in any file of the part`).

### Task 2: Parts in the report model

**Files:**
- Modify: `core/report-page.js` (model), `test/report-page.test.mjs`

**Interfaces:**
- Consumes: `D.modules[].{id, name, files, code}`, `D.screens[].{id, name, files}`, `D.coverage.parts[].{id, total, covered}`, the existing `specs` entries.
- Produces: model `parts: [{ id, name, kind: "module" | "screens" | "other", specs: Spec[], rules, stories, broken, stale, lost, proven, weak, untested, outdated, files, tone, health, covered: { total, covered } | null }]`, `rows()` now returns parts (same filters, plus `filter: "nospec"`; same sorts, plus `sort: "covered"`), and `partOf(specPath) → part id`. `counts` unchanged (summed over spec files, as now). Health for a part without spec files: `"No spec"`, tone `"none"`.

Assignment, in order: the part (modules, then screens, in data order) whose `files ∪ code` holds the most of the spec's cited files, ties to the first; else the part whose id equals the spec folder or prefixes it (`orders-…`); else a part of kind `"other"` per spec (id = spec path, name = the spec's name). With no modules and no screens, every spec is its own `"other"` part, which keeps today's table.
